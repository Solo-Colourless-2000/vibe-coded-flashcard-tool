MongoDB保存機能を追加する

TOTAL RECALL 0.2.1の現在のファイル構成から始める、初心者向けの追加開発実習。2026-10-08版。

関連ファイルを往復し、小さな変更と確認を積み重ねます。

型 → Nodeの保存処理 → HTTP → ブラウザーの通信 → テスト → 二つの起動入口 → 下書き → 保存hook → 設定画面 → RecallApp接続の順で進めます。実装は12章・95工程です。各工程に、開くファイル・探す文字・変更前後の短いコード・理由・確認結果・失敗時の確認先を記載しています。

これは新しい追加開発マニュアルです。このHTMLを作成した時点で、実際のアプリ・README・既存メインマニュアルへ変更は加えていません。本文の変更は、読者がこれから作る実習コピーに適用する手順です。

準備はOS別です。WindowsのPowerShellで進める方は「作業コピー」、LinuxのBashで進める方は「Linuxの準備」を使います。バックアップ・DB設定・95工程のコード・移行の考え方は共通で、初回起動には両OSのAPI確認コマンドを記載しています。

この別冊で作る機能

  • 保存済みセット、カード、学習の途中経過、削除済みセットIDをMongoDBへ保存します。未完成の下書きもMongoDBの別文書へ保存します。
  • ブラウザーは同じアプリのHTTP APIへ通信し、Node.jsだけがMongoDBの接続情報を持ちます。
  • 空のDBなら空の一覧を表示します。接続障害や破損を空データとして扱って上書きしません。
  • 同時編集の競合と保存結果が不明な通信障害では書込を停止し、画面の入力を利用者がJSONへ退避できます。
  • 元アプリが書き出したJSONバックアップを、内容確認後にMongoDBへ一度復元します。元の保存データは削除しません。

一つずつ書き、ファイルを往復する

完成コードを一つのファイルへ貼る進め方ではなく、部品を作り、検証し、最後に画面へつなぎます。

毎工程の共通操作

  1. VS Codeで実習コピーのフォルダーを開きます。ターミナルの現在位置もコピーであることを確認します。
  2. 工程に書いたファイル名をコピーし、Ctrl+Pで貼り付け、Enterで開きます。先頭のapp/やserver/も含めます。
  3. 「置換」ではCtrl+Fで変更前コードの特徴的な一行を検索します。変更前のまとまりを選択し、変更後の短いコードに置き換えます。元ファイル全体を消しません。
  4. 「追記」ではCtrl+Endで末尾に移り、ファイル全体の最後の閉じ波括弧の後へ空行を挟んで追加します。関数の中へ誤って入れないよう、周囲の括弧を見ます。
  5. 「新規作成」ではエクスプローラーで親フォルダーを作り、記載の拡張子どおりにファイルを作成します。最初の小さな骨組みを入力し、後の工程で同じファイルへ戻って処理を足します。

画面・Node・MongoDBの役割を分ける

このプロジェクトはVinextを使っています。保存APIは既存のNode入口に接続します。

通信が進む順番

編集・学習画面（ブラウザーのReact）
↓ useMongoStudyStorage／draftStorage が保存を依頼
store → transport（保存の順序・世代・HTTP）
↓ 同じオリジンへ GET /api/mongo/state または PUT /api/mongo/state
Node HTTP入口（開発はvite.config.ts、通常起動はstart-local.mjs）
↓ server/mongo/http.mjs が本文・Origin・methodを検査
repository → MongoClient（検証・競合防止・接続プール）
↓ Nodeだけが.env.localを読み、MongoDBへ接続
MongoDB（保存成功の応答） → Node → ブラウザー → 保存済み表示

現在のbuildはRSC・SSRのCloudflare用環境も持ちます。一方、開発のViteミドルウェアと通常起動のNode HTTPサーバーはNode上にあります。この教材はその入口でAPIの応答を完了し、MongoClientをWorkerやブラウザーの束へ混ぜません。app/api/route.tsを作るだけの一般的なNext.js例へ置き換えないでください。

ViteのconfigureServerは開発サーバーのミドルウェアを追加する入口です。Vite公式：configureServer。通常起動には同じ関数を別途登録します。

保存する文書は二つ

recall_state_id: "main"sets（StudySet[]。カード・進捗を含む）、deletedSetIdsセット作成・編集・削除・JSON復元、および学習のsets更新後500ms

これは構造を説明する例で、手動でDBへ貼るデータではありません。UUIDの欄の日本語は説明用です。実際はコードがUUIDと日時を作ります。DB文書がまだない最初のGETはrevision:null、updatedAt:null、空のvalueを返すだけです。DBへ挿入せず、接続障害なら503を返します。

「先に読んだ世代のままなら保存する」

二つのタブが世代Aを読んだ後、タブ1が保存して世代Bになると、タブ2の「Aを読んだ」という保存要求は409で停止します。更新は_idとrevisionを条件にしたreplaceOneで一文書へ実行するので、条件に合わない古い状態は置き換えられません。初回insertが競合した場合も409です。

MongoDBは一文書の更新を原子的に処理し、更新条件に期待する現在値を入れて競合を防ぐ使い方を案内しています。この教材のrevision条件はその考え方を使っています。MongoDB公式：一文書更新と条件

operationIdは同じ保存要求の識別子です。最新保存と同じID・同じ内容なら同じ結果を返せます。ただし、後の別保存が済んだ古い要求を無制限に再適用する履歴機能ではありません。ブラウザーは競合時に自動上書きや自動mergeをしません。

たとえば解答を直した時、各部品は何をするか

  1. 入力画面で解答を「apple」から「Apple」へ直します。編集中は下書き、保存ボタンでは保存済みセットが対象になります。
  2. hook／draftStorageが対象の値をstoreへ渡します。storeは前の要求が終わるまで待ち、確認済みのrevisionを今回の要求へ付けます。
  3. transportはJSONを同じアプリの固定APIへ送り、httpは受け付ける条件を確認します。Nodeのrepositoryは形式を検証し、同じrevisionならDBへ保存します。
  4. DBの確認結果がNodeから戻り、transportが応答の形を確認してから、storeとhookが「保存済み」へ進めます。返事が得られる前の画面変更だけでは保存成功の根拠になりません。

正常・競合・結果不明を区別する

結果意味画面の扱い
200＋検証できた応答DB読込または保存が確認できた確認済みのrevisionを更新。対象の画面内容と一致すると保存済み表示。
400／413入力・容量などを拒否した保存を止めて原因を確認。移行元JSONは保持。
409別の保存が先に更新した書込停止。入力を退避してからDBを再読込。
GETの503DBを読めない、または保存文書が不正空のDBと扱わない。画面を保護停止。
PUTの5xx／タイムアウト／切断／不正な200応答書き込まれたか確認できない「未保存」と断定しない。入力を退避後、再読込でDBの実際の状態を確認。

結果不明の具体例は、NodeがDBへ保存した直後にブラウザーまでの返事が切れる場合です。DBには「Apple」があるかもしれませんが、画面では確認できません。同じ内容を新しい要求として無条件に保存すると、間に別の編集があった時に失われます。そのため入力をJSONに退避し、接続を直してDBを再読込します。

セット文書と下書き文書は別々の操作です。セット保存が成功しても、続く下書きクリアだけが失敗する場合があります。その場合はセットの成功を保持して警告を出し、再読込後に残った下書きを確認します。二つの文書を同時に成功させるトランザクションはこの教材には含みません。

ブラウザーのReactメモリーはタブを閉じると失われます。ネットワークが必要なので、保存済み表示を確認してから閉じてください。失敗時にローカル保存へ自動で切り替える機能は作りません。

一文書にまとめる理由と容量の制限

現行の保存契約はセット配列と削除IDを一括確定する形です。教材ではstateを一文書にまとめ、既存の保存・削除を原子的に置き換えます。その代わり大きなデータ全体を一文書に収める必要があります。

MongoDBの一文書のBSON上限は16MiBです。MongoDB公式：BSON文書の上限。この教材はAPIのUTF-8 JSONを12MiB、保存予定のBSONを14MiBまでに制限します。1MiBは1,048,576バイトです。文字数とは一致しません。

元アプリの上限より小さいデータ量で拒否される場合があります。移行ファイルの見た目のサイズだけではなく、通信するcommand全体とBSONの実サイズをコードで測ります。超過したら元データを残し、セットの分割・必要な範囲の移行、または「セットごとの文書＋削除記録＋複数文書トランザクション」への設計変更を検討します。この別冊の上限だけを増やして移行しません。

元アプリとデータを保管して準備する

保存方法を変える実習は、現在のアプリと別のフォルダー・別のブラウザープロファイルで行います。

この章のバックアップとブラウザープロファイルは両OS共通です。「コピー先」「Node・依存」のコマンドはWindows PowerShell用です。Linuxの方はバックアップを保管した後、Linuxの準備の対応する手順で進めます。

先に元アプリからバックアップを作る

  1. 現在のアプリで未完成の編集があれば、内容を確認してセットとして保存します。バックアップに含まれるのはセット・カード・進捗・削除IDであり、未確定の下書きは含まれません。
  2. 左下の保存先設定を開き、「バックアップを書き出す」を押します。生成されたTOTAL RECALL形式のJSONを、元プロジェクトと実習コピーの外の自分のバックアップ用フォルダーへ保管します。
  3. ファイルが実際に存在すること、0バイトでないこと、書き出した日時、セット数・カード数を記録します。機密な内容をオンラインのJSON検証サイトへ貼りません。
  4. 元アプリを起動したターミナルでCtrl+Cを押します。元アプリのIndexedDBやフォルダー保存先のJSONは削除しません。
Firefoxでフォルダー選択のボタンがない場合でも、元アプリのJSONバックアップ書き出しは別の操作です。この移行ではフォルダー選択APIを使いません。元アプリから手動で書き出したバックアップを用います。

コピー先を空から作る

以下はWindows PowerShellの例です。コピー元はこのマニュアルの基準フォルダーです。実際の名前が違う場合は、最初の一行だけ自分のプロジェクトへ合わせます。コピー先は新しい専用フォルダーにします。既に存在する場合は中身を削除せず、別の新しい名前を選びます。

$practiceSource = (Resolve-Path -LiteralPath 'F:\learning-tool\vibe-coded-flashcard-tool').Path
$practiceTarget = 'F:\learning-tool\total-recall-mongodb-practice'
if (Test-Path -LiteralPath $practiceTarget) { throw 'コピー先は既に存在します。新しい名前を選んでください。' }
New-Item -ItemType Directory -Path $practiceTarget
robocopy $practiceSource $practiceTarget /E /XD .git node_modules dist .next .vinext .wrangler release recall-data learning-sets /XF .env .env.* *.key *.pem *.pfx *.p12
if ($LASTEXITCODE -ge 8) { throw 'コピーに失敗しました。表示されたファイルと権限を確認してください。' }
Set-Location -LiteralPath $practiceTarget
code .

robocopyの終了コード0〜7は、差分などの正常な状態を含みます。8以上は失敗です。/Eはフォルダーも含めてコピーする指定、/XDは除外フォルダー、/XFは除外ファイルです。削除・同期をする/MIRや/PURGEは使いません。Nodeの依存やビルド結果は新しく作り、秘密の.envは持ち越しません。

手動コピーでも構いません。その場合も、app、public、scripts、tests、docsとルートの設定ファイル（.npmrc・.gitignoreを含む）が必要です。実際の学習データを保管した独自フォルダーがプロジェクト内にある場合は、そのフォルダーもコピー対象から外します。

codeコマンドが見つからなければ、VS Codeの「ファイル → フォルダーを開く」でコピー先を選びます。以後の本文の相対ファイル名は、すべてこのコピーの中を指します。元フォルダーを同時に開いて混同しないよう、ウィンドウのタイトルも確認します。

ブラウザーも別のプロファイルを作る

保存領域はプロジェクトフォルダー名で分かれません。同じブラウザープロファイルで同じhttp://127.0.0.1:3000を開くと、元アプリのブラウザー保存領域と同じオリジンになります。Chrome／Firefoxのプロファイル管理で実習用プロファイルを作り、元アプリを使うプロファイルから分けます。元の閲覧データを削除する操作は不要です。シークレット／プライベートウィンドウは終了時に領域が消えるため、実習用の通常プロファイルを使います。

export function createMongoTransport<T>(
  kind: MongoKind, parseValue: (input: unknown) => T, fetcher: typeof fetch = fetch,
): MongoTransport<T> {
  if (!Object.hasOwn(API_PATHS, kind)) throw new Error("invalid_api_kind");
  const path = API_PATHS[kind];
  async function request(command?: MongoCommand<T>): Promise<MongoRecord<T>> {
    const body = command ? JSON.stringify(command) : undefined;
    if (body && new TextEncoder().encode(body).length > MAX_API_BYTES) {
      throw new MongoRequestError(413, "body_too_large");
    }
    let response: Response;
    try {
      response = await fetcher(path, {
        method: command ? "PUT" : "GET", cache: "no-store", mode: "same-origin",
        credentials: "same-origin", signal: AbortSignal.timeout(12000),
        headers: { "X-Recall-Mongo": "1", ...(command ? { "Content-Type": "application/json" } : {}) },
        body,
      });
    } catch (error) {
      if (command) throw new MongoWriteUncertainError();
      throw error;
    }
    if (!response.ok) {
      if (command && response.status >= 500) throw new MongoWriteUncertainError();
      throw new MongoRequestError(response.status, "mongo_http_error");
    }
    try { return parseMongoRecord(await response.json(), parseValue); }
    catch (error) {
      if (command) throw new MongoWriteUncertainError();
      throw error;
    }
  }
  return { read: () => request(), write: (command) => request(command) };
}

function wireRequest(url, options = {}) {
  return new Promise((resolve, reject) => {
    const body = options.body;
    const request = httpRequest(url, { ...options, headers: {
      ...options.headers, ...(body === undefined ? {} : { "Content-Length": Buffer.byteLength(body) }),
    } }, response => {
      let text = "";
      response.setEncoding("utf8");
      response.on("data", chunk => { text += chunk; });
      response.on("end", () => resolve({ status: response.statusCode,
        json: async () => JSON.parse(text) }));
    });
    request.on("error", reject);
    request.end(body);
  });
}

保存停止画面の安全な使い方

  1. タブを閉じず、画面に残っているセットと入力中draftをそれぞれ別名のJSONへ退避します。
  2. 初回読込失敗なら画面は空です。そのJSONを元バックアップの代わりに扱ったり、移行元へ上書きしたりしません。
  3. 接続・権限・容量・競合の原因を直します。Node設定を変えた時はサーバーを再起動します。
  4. 「退避後にDBを再読込」を押し、確認ダイアログを読んで再読込します。未保存のReactメモリーは消えるので退避を先にします。
  5. DBの最新内容を見て、退避した入力のどの部分を戻すか判断します。セット退避は検証済みバックアップ形式なので明示復元に使えますが、全体置換です。draft退避は確認用のJSONで、セット復元には使えません。

主保存がDBでもバックアップは別に必要

MongoDBに最新状態があることだけでは、誤削除・誤復元・運用上の障害から過去状態を戻せるとは限りません。節目にJSONを書き出して、保存場所・日時・復元確認の記録を残します。管理しているDBサービスのバックアップ機能は、自分のプラン・環境の公式説明を確認して設定し、実際の復元も確認します。設定したつもりで未検証のバックアップを唯一の復旧方法にしません。
